# 项目接续：让新会话一次读取就接上项目现状（Project Brief）

> 状态：方案稿 v0.1（2026-11-23），待负责人拍板 §7 的四个问题后进入实现。
> 起点：负责人提出"新开会话重读上下文"太贵，一次就花掉约 16% 的 5 小时额度，并给了一份与 GPT 讨论后的提案。本稿审查那份提案，对照现有代码收窄成最小可交付的方案。
> 约束：`core-no-embedded-llm`、`memory-distillation-by-agent`、`host-does-query-preprocessing`（D23 不按内容分类）、D24/D33 产品边界、第二轮 P0-1 的记忆信任规则。

## 0. 结论

1. **方向对，但提案里的实体多了一半。**
   - "项目状态"可以做成一种新的记忆类型 `state`：复用 `memories` 表已有的替代链（`supersedes`）、证据、作者、确认状态，不用新建 `project_snapshots` 表。
   - 真正缺的只有两样："项目身份"（别名、多路径、非代码项目），以及"状态是否过期"的确定性判断。
2. **省额度的关键不在接口，而在让宿主先读状态。**
   - 这次花掉 16%，是因为宿主一上来就派三个子 Agent、扫原始事件；它没有"上次确认的状态"可以接续，也没有"先读状态、只查过期部分"的约束。
   - 只加一个 `get_project_brief`，宿主照样可能不调用。所以要两手：Claude Code 用 SessionStart hook 在会话开始时自动注入当前项目的简报，其他宿主靠 MCP 说明和 skill 引导。
3. **Penpal 不做总结。**
   - Penpal 只做三件事：存宿主写下的状态；用确定性规则算出"状态写下之后又发生了什么"；把两者拼成简报。
   - 提炼和改写由宿主完成。这样守住"核心不内置大模型"，也不会滑回 D24 下线的日报、周报。
4. **交付顺序和提案相反：先接续，后身份。**
   - 代码项目用现有的"文件夹名即项目"规则就能先跑通，第一个 PR 就能直接省额度。
   - 别名和非代码项目放到第二个 PR。

## 1. 问题拆解（已证实 / 判断 / 未知）

| | 内容 |
|---|---|
| 已证实 | 现在的 `search_context` 返回原始事件和记忆，没有"项目当前状态"这一层，宿主每次只能从历史里重新拼。 |
| 已证实 | 记忆的 `project` 字段等于文件夹名（`foundation/project.py` `normalize_project`），精确匹配。它不认别名；没有文件夹的项目（比如面试准备）根本表达不了。 |
| 已证实 | 记忆已经有类型（fact / preference / decision / procedure）、项目范围、替代链、证据、作者（`source_tool`）、确认状态（`confirmed_at`），以及可以放长文本的 `detail`。 |
| 已证实 | Claude Code 的 SessionStart hook 能往会话开头注入文字，本机现有的 hook 就在这么用。 |
| 判断 | 额度大头花在宿主的调查行为上（读文件、子 Agent、扫事件），Penpal 一次调用本身很便宜。所以效果取决于宿主有没有"先读简报、只查过期部分"的纪律。 |
| 未知 | Codex、Cursor、OpenCode 能不能在会话开始时注入文字，各家怎么做，要逐个核实。 |
| 未知 | 一份简报多大合适：太短接不上，太长每个会话都在白花额度。先定 1.5k token 上限，用评测校准。 |

## 2. 对提案逐条的取舍

| 提案 | 取舍 | 理由 |
|---|---|---|
| 区分"发生过什么"和"项目现在什么状态" | **采纳**，这是核心 | 原始历史已经有了，缺的是状态层。 |
| 新建 `project_snapshots` 表 | **不采纳**，改成记忆类型 `state` | 版本、作者、证据、确认、删除、导出、隐私脱敏都已经在 `memories` 上实现。另起一张表，等于把这些重做一遍，还多一个"同一结论两个来源"（违反 D36）。 |
| 稳定的项目 ID、别名、非代码项目 | **采纳**，放 PR-B | 这是真缺口。但先做它会拖住第一份价值。 |
| 用版本号防止多个 Agent 互相覆盖 | **采纳**，不加字段 | 写新状态时必须带上它要替代的当前版本 id；如果已经有别人写了更新的版本，拒绝并返回最新版本（比较后再交换）。替代链本身就是版本号。 |
| 后台被动更新：标记变化的模块和证据 | **部分采纳** | 能做的是确定性的"增量清单"：状态写下之后，这个项目又有几次 git 提交、几个 AI 会话、改了哪些文件，以及最近几条提交标题。不做"哪个模块变了"这类语义判断，那就成了内容分类。 |
| 会话结束时自动写检查点 | **采纳，但只能是软约束** | hook 本身不能让模型写总结，只能靠 skill 或说明引导宿主写。宿主意外退出时就没有总结。兜底是下次读简报时看到"已过期"，再补写。 |
| Memory Consolidation（合并、去过期、识别冲突） | **收窄** | 过期由确定性规则判断。"冲突"只认结构性的：两个宿主各自基于同一个旧版本写了新版本。不认语义上的矛盾。 |

## 3. 方案

### 3.1 数据：`state` 记忆

- 类型 `state`，必须是项目范围。每个项目同一时刻只有一个现行版本，旧版本按替代链保留，`penpal memory history` 可以查。
- `content` 放一句话现状，比如"P1 第三轮已合并，P2 未开始"。`detail` 用固定小节，宿主按模板写，Penpal 只校验小节是否齐全：
  - 已完成
  - 进行中
  - 阻塞
  - 下一步
  - 未验证 / 待确认
- 必须带 `evidence_ids`，或者 git 提交号、PR 号这类可核对的锚点。
- 与第二轮信任规则的关系：宿主写的 `state` 默认"未确认"。它必须跨宿主共享，否则失去意义。简报照样展示，但标明作者、时间和"未经你确认"。用户可以 `penpal memory confirm`，确认后标记消失。

### 3.2 读取：`get_project_brief` 和 `penpal brief`

- 两个入口，一套实现：
  - MCP 工具 `get_project_brief(projects?)`：不传项目时，用宿主当前目录对应的项目。
  - CLI `penpal brief [--project X] [--format hook]`：给 SessionStart hook 用，不经过 MCP 往返。
- 简报内容按顺序排列，总长不超过 1.5k token：
  1. 现行 `state`：现状，加 detail 的五个小节，以及作者、时间、确认状态。
  2. **新鲜度**：状态写下之后，这个项目新增的 git 提交数、AI 会话数、最近活动时间，以及最多 5 条提交标题。超过阈值就标"可能过期"，并给出那批事件的 evidence_id。阈值先定为任一新增大于 0 就提示，再用评测调。
  3. 这个项目已确认的 decision 记忆，最多 5 条，只列标题。
  4. 待确认项：未确认的记忆条数、待批准的配方条数。
- 授权：简报走和 `search_context` 一样的授权、分类和脱敏，并附 `content_notice`。hook 调 CLI 时用这个宿主的 token，范围和它通过 MCP 能读到的一致。

### 3.3 写入：`commit_memory` 扩展

- `commit_memory` 接受 `type: "state"`。如果这个项目已经有现行状态，就必须带 `supersedes`，并且只能指向当前现行版本。指向旧版本时返回 `status: "conflict"` 和最新版本，宿主合并后再写。
- skill 和 MCP 说明里写明两件事：
  - 什么时候写：会话结束前，或者某件事完成、方向改变时。
  - 怎么写：先读简报，只改有变化的小节，没有核实的进展放进"未验证"，不写成"已完成"。

### 3.4 项目身份（PR-B）

- 新增 `projects`：项目 id（slug）、显示名、别名、路径（可以多个，包括非代码目录）、仓库地址。
  - 用户用 `penpal project add / alias / bind-path` 管理。
  - 宿主可以提议绑定，比如"当前目录属于某个已登记项目"。提议和配方一样，等用户批准。原因是绑定错了会把两个项目的记忆和状态混在一起。
- 现有的"文件夹名即项目"作为默认身份保留：没登记的项目照常可用，登记后别名和多个路径都指向同一个 id。
- 非代码项目（面试准备、知识库文档）：新鲜度只能来自绑定的路径或文档；没有绑定的来源，简报标注"新鲜度未知"，不假装知道。按 D23，Penpal 不会按内容去猜一段浏览记录属于哪个项目。

### 3.5 宿主接入

| 宿主 | 读 | 写 |
|---|---|---|
| Claude Code | SessionStart hook：`penpal brief --format hook`（`penpal connect` 时可选写入） | skill + MCP 说明 |
| Codex / Cursor / OpenCode | MCP 说明要求先调 `get_project_brief`；如果有会话开始时的注入入口，再接（§1 的未知项，先核实） | 同上 |

注入的风险：简报每次会话自动进入上下文，比按需搜索更容易被提示注入利用。缓解措施有四条：
- 简报只拼宿主写的 `state` 和确定性的统计，不原样带入原始事件正文；
- 包在明确的数据块里，并附 `content_notice`；
- 长度有上限；
- 未确认的内容有标记。

## 4. 不做什么

- Penpal 不生成总结、不写周报日报，也不在后台调用模型补写状态。
- 不按内容判断事件属于哪个项目（D23）。
- 不把仓库里 `brain/` 的内容复制进 Penpal。代码仓库的长期决策以仓库自己的 brain 为准，简报只放一行提示"此仓库有 brain/，先读 brain/index.md"（见 §7 问题 3）。

## 5. 分期与验收

| PR | 范围 | 验收 |
|---|---|---|
| **PR-A 接续** | `state` 类型、比较后再交换的写入、`get_project_brief` / `penpal brief`、基于现有事件标签的新鲜度、Claude Code SessionStart hook、skill 写入引导 | 在一个代码仓库里新开 Claude Code，第一轮回答"现状和下一步"只用一次简报，不派子 Agent。git 在状态之后有新提交时，简报必须标"可能过期"。 |
| **PR-B 身份** | `projects`、别名、多路径、非代码项目、宿主提议加用户批准 | 三个真实形态的合成夹具（代码仓库、带别名的仓库、无代码的准备类项目）各自归属正确，互不串。多项目查询一次返回。 |
| **PR-C 对账** | 冲突检测（并行写入）、`memory history`、过期阈值校准、评测门禁 | 两个宿主基于同一版本并行写入时，第二个收到冲突，不静默覆盖。门禁见 §6。 |

## 6. 评测（并入 `docs/Penpal_Eval_PRD.md`）

新增"接续"场景。用合成项目回放：先写入状态，再制造增量，然后让全新会话回答"现在什么进展、下一步做什么"。

| 指标 | 口径 | 门槛（初定） |
|---|---|---|
| 接续成本 | 从会话开始到第一个正确回答，消耗的 token 和工具调用数，和不用简报对比 | token 下降 70% 以上 |
| 状态准确 | 回答里的完成、进行中、下一步和标准状态一致 | 90% 以上 |
| **过期不冒充** | 有增量时，回答必须指出可能过期，不能把旧状态当最新进度说 | **0 次违规，硬门禁** |
| 未验证不宣称完成 | 状态里"未验证"的条目，回答中不能说成已完成 | **0 次违规，硬门禁** |

负责人自己的真实验收：PR-A 合并后，新开会话问一句项目现状，看这一次花掉多少 5 小时额度，和这次的 16% 对比。

## 7. 待负责人拍板

1. **宿主写的状态，要不要你确认后才跨宿主共享？** 建议：直接共享并标"未确认"。如果每次都要确认，接续就断了；风险靠作者标记、长度上限和 `content_notice` 兜住。
2. **会话开始时自动注入，还是只在宿主调用时返回？** 建议：Claude Code 自动注入当前目录对应的项目（1.5k token 以内），其他项目按需调用。每个会话固定多花一点，换来不再重做调查。
3. **代码仓库已有 `brain/` 时，简报要不要带它的内容？** 建议：只放一行提示，不复制内容，免得同一结论两个来源。
4. **非代码项目第一期要不要做？** 建议：放 PR-B。PR-A 先在代码仓库验证"省额度"成立，再扩展。
