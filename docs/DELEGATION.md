# 派活、验收与 token 成本

> 本文件给主控（Claude Code 主会话）用，不必附给 worker。worker 只需遵守 `docs/ENGINEERING.md` 和简报。
> 两个目标：
> - 合进 main 的代码是干净的（§5 验收）；
> - 花出去的 token 都值得（§1、§2）。

## 1. 钱花在哪
**数据来源**：2026-10 一个连续 20 天的主会话（5,688 轮），加上它派出的 83 个子 Agent，按 API 标价折算。折算只用来比较各项的相对大小；如果是订阅制，这些数字体现为额度消耗的快慢。

- **主会话与子 Agent**：主会话约占全部 Claude 消耗的 80%，子 Agent 约占 20%。Codex 和 agy 用各自的额度，不计在内。
- **主会话的构成**：重读上下文约占一半，写入上下文和生成输出各约占四分之一。
- **上下文大小**：每轮上下文的中位数是 16.4 万 token。按这个大小，每轮仅重读一项的成本，就是上下文 4 万时的 4 倍。
- **重读次数**：每个进入上下文的 token，平均会在后续各轮里被重读约 50 次。折算下来，往上下文里放 1 个 token，成本接近生成 1 个输出 token。
- **子 Agent 规模**：每个子 Agent 的轮数中位数是 77，其中 20 个超过 100 轮。Haiku 子 Agent 有 43% 的轮次输入超过 10 万 token，而 Haiku 5.5 的输入超过 10 万后，单价变为原来的 5 倍。

**结论**：最大的杠杆是主会话的上下文大小和轮数，其次是子 Agent 的规模。把输出写短只能省下一小部分。

## 2. 主会话的五条规则（按收益排序）
1. **一个工作流一个会话。**
   - 一个 PR 或一个问题做完就收尾：决策写进 brain，交接写进 PR 描述，下一件事开新会话。
   - 新会话的固定开销（系统提示、工具清单、常驻文件）只付一次；按估算，一个任务超过约 15–20 轮，就比继续留在大会话里便宜。
   - 不在同一个会话里跨天堆积任务。如果必须连续做，在每个阶段结束时（例如合并之后）主动 `/compact`。
2. **工具输出按输出 token 的成本对待。**
   - 先计数再看内容（`wc`、`--jq`、`head`），文件按行段读取。
   - 长日志和测试输出写进 scratchpad，只读摘要和失败项。
   - 预计超过约 200 行的结果，不直接放进上下文。
3. **减少往返。**
   - 互不依赖的调用放在同一轮。
   - 长任务放到后台，等完成通知，不轮询。
   - 等 CI 时用一个后台循环，一次等到全部检查结束。
4. **读得多、结论少的活交出去**（见 §3）。主控只收结论和 diff，不收过程。
5. **用到才加载。**
   - 技能、MCP 工具和大文档，用到时才加载。
   - 常驻文件（CLAUDE.md、AGENTS.md、被导入的 BRAIN.md、MEMORY.md）每轮都会被重读，要保持短小。

## 3. 派不派、派给谁
先回答三个问题：
- 需要本次对话里的上下文吗？需要就自己做。
- 中间产物多、结论少吗？是就派出去。
- 能写出可执行的验收标准吗？写不出就先别派，把问题想清楚再说。

默认先派给 Codex 或 agy，因为它们不占 Claude 额度；它们做不了或失败了，再派 Claude 子 Agent。

| 情况 | 交给 | 原因 |
|---|---|---|
| 小改动（约 3 个文件以内，上下文已在手） | 主控自己 | worker 冷启动要重建上下文，比直接改更贵 |
| 方案取舍、验收、给负责人的汇报 | 主控自己 | 依赖本次对话，不能外包 |
| 前后端实现与清理（HUD、CLI、安装 / launchd、打包） | agy，在独立工作区里做 | 负责人定的分工；不占 Claude 额度 |
| Agent 相关实现（MCP、宿主接入、记忆召回、评测），以及批量机械改动 | Codex（`gpt-6.1-terra`），在独立工作区里做 | 同上 |
| 搜索、摸底、统计，只要结论 | Codex `-s read-only` 或 agy `--mode plan`；要在本会话里快速拿到结论时，用 Claude 子 Agent（Haiku 5.5） | 读到的内容不进主上下文 |
| Codex 和 agy 都做不了的实现或排查 | Claude 子 Agent，Haiku 优先，失败后换 Sonnet 5.5 | 兜底 |
| 交叉审查、第二意见 | 用一个与作者不同的模型：agy `--mode plan` 或 Codex `-s read-only` | 视角独立 |

规模上限：
- 一个子任务预计不超过 50 轮，上下文不超过 10 万 token。超出就拆分，或改派 Codex / agy。
- Haiku 只接搜索、统计和机械改动；需要判断的派给 Sonnet 或 Codex。
- 同时在跑的 worker 不超过 3 个，各自改的文件不能重叠。

## 4. 简报
简报要自包含：给文件路径，不贴全文。模板：

```text
# 任务：<一句话目标>
仓库：<工作区路径>（分支 <name>）。先读 docs/ENGINEERING.md 并遵守。
## 目标      做完后什么变了，对谁有用
## 输入      相关文件路径、现象、已知数字；不贴大段代码
## 只做      编号清单，每一条都能检查
## 不做      明确排除的文件、目录和做法
## 安全约束  原样粘贴下方的固定段落
## 验收标准  可执行的命令和预期输出；主控会逐条复核
## 报告      中文，300 字以内：改了什么（文件数、各类问题的处数）、验证结果、没做完的、拿不准的；不贴日志和 diff
```

固定安全段落（原样粘贴）：
> - 不读 ~/.penpal、~/.keypulse、~/.claude、~/.codex、~/.cursor、~/.zsh_history、~/Library、浏览器数据、~/.memmy。
> - 不运行 launchctl，不启动 GUI，不做系统级安装。
> - 测试只用 `penpal-isolated-pytest -q <路径>` 运行（会使用临时 HOME）；不在后台运行任何东西。
> - 不 commit，不 push。
> - 仓库是公开的：代码、测试、注释里不写真实数据或本机路径。

调用方式：
- **Claude 子 Agent**：用 Agent 工具，并写明 `model`；需要改代码的，设 `isolation: worktree`。
- **Codex**：在后台运行下面的命令，等完成通知。只读审查把 `-s workspace-write` 换成 `-s read-only`。
  ```text
  codex exec -m gpt-6.1-terra -s workspace-write -C <工作区> --skip-git-repo-check --output-last-message <报告文件> "$(cat <简报>)" </dev/null
  ```
- **agy**：在工作区里运行下面的命令；只读审查用 `--mode plan`。不得使用 `--dangerously-skip-permissions`。
  ```text
  agy --print '<简报>' --mode accept-edits --sandbox --output-format json
  ```
  agy 在无人值守模式下，会拒绝白名单以外的所有命令，而只要有一条命令被拒，整次运行就没有任何产出。白名单是：`penpal-isolated-pytest`、`bash -n`、`shellcheck`、`git diff|status|log`。所以给 agy 的简报必须写明以下几点：
  - 只能用白名单里的命令；
  - 开工前不跑基线测试；
  - 不在后台运行任何东西；
  - 不用管道、重定向和环境变量前缀。
  - 不读工作区以外的文件：无人值守模式会拒绝读取工作区外的文件，结果同样是整次运行没有产出。所以 ub-lite 要去掉文件头后把全文贴进简报，不能只写路径；Codex 能读路径，不受此限。

  如果运行中断，用 `--conversation <id>` 接着跑。

## 5. 验收清单
主控逐条做；worker 说"通过"只当作线索。
1. **范围**：`git diff --stat` 只包含约定的文件；越界就退回。
2. **门禁**：主控自己跑 `ruff check penpal tests scripts evals`、`lint-imports` 和相关测试；合并前 CI 必须全绿。
3. **读 diff**：
   - 机械改动看 stat，每类抽查 2–3 处；
   - 需要判断的改动逐行看；
   - 修 bug 新加的测试，要确认它在旧代码上会失败（章程底线 5）。
4. **公开仓库**：diff、提交信息、PR 描述里没有真实路径、用户内容或令牌。新增的日志只记事件类型、计数和异常类型，不记 `str(exc)`。
5. **遗留**：每个 `noqa`、TODO 和被跳过的测试都写了原因；没有调试打印，没有注释掉的代码。
6. **报告对账**：报告里说做了的，diff 里都要有；报告里的数字，自己复算其中一项。

不通过时：写明哪一条没过，退回一次。第二次仍不通过，主控自己接手，或缩小范围重新派，不进入第三轮。

## 6. 收尾
- 合并后删除工作区；有新决策就写进 brain。
- 给负责人的汇报写清：派了几个 worker、验收是否一次通过、哪些需要手测。
- 本文件的数字每季度用会话记录重算一次，规则随数据调整。
